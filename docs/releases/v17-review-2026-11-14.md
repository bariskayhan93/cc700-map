# v17 review and next firmware boundary

Reviewed 2026-11-14 against the new [ride incident report](../reports/ride-map-loss-2026-11-13.md),
the sibling patch sources, saved v16/v17 images, and the already acquired ride
files. **Do not treat the current v17 image as ready to flash.** Two loader
counterexamples remain. No device connection, reset, read or write occurred in
this review. The last reported installed firmware is v16; it was not read again.

## Findings, in priority order

### 1. Adjacent-section guard can retain a stale block indefinitely

`../cc700-backup/patch/src/blk.c:76..77` accepts a position-based section only
when `abs(candidate_section - firmware_section) > 1`. Section adjacency is not
a distance bound. If the matcher stalls just before a map-block boundary, the
position can travel the entire next section without changing the loaded block.

A host probe executes the complete current **`cc_pos` + `cc_blk` C bodies**,
substituting address adapters for firmware calls and supplying point payloads
with section IDs at +40. A straight two-section route, firmware section 0,
and position 900 m into section 1 still selects section 0's block. The fixture
uses distinct block offsets. This demonstrates incorrect block retention;
it does not claim to reproduce a rendered blank screen on the device.

Before flashing: replace this numeric adjacency rule with a distance-based
policy in the section domain, and retain this case as a regression.

### 2. Hysteresis still mixes point-segment and section indices

`blk.c:73` passes the firmware section to `cc_nearest_sec`, but the helper
at `blk.c:24..31` treats that argument as a **point-segment index** when it
calculates the current distance and applies its 25 m preference. Reading +40
afterward corrects the final lookup domain, but not the preference calculation.

A full-loader C probe supplies three sections with a return pass 10 m from
the outbound pass. Firmware section 2 and the rider on section 2 select block
0, because point segment 2 belongs to section 0. This contradicts the stated
policy of keeping the current section within the distance margin. The existing
nine helper probes use one segment per section, which hides this mismatch.

Before flashing: calculate the current section's minimum distance across its
own segments; distinguish point index, point-segment index, section ID and map
offset throughout the interface. Shared endpoint ownership needs the loader's
actual convention, not an inferred section-start table.

### 3. Replay callback aliased both ends of a segment — corrected locally

The former callback in `tools/cc700_replay.py` returned the same mutable two-float
buffer for every point. In `seg_d2(pos, pt(i), pt(i+1), ...)`, both pointers
therefore referred to one endpoint after both callbacks returned. A long segment
through the rider plus a nearby short segment chose segment 1 through that
callback, but segment 0 through stable point addresses.

The callback now returns distinct addresses in the retained coordinate array.
On the acquired ride this changes **210/576 selected segment indices** and
**one selected block** under the existing Python section reconstruction. The
aggregate coverage result happens to stay the same; that does not excuse the
old callback. A permanent regression checks independent endpoint storage.

### 4. FIT decoder and evidence accounting overstated replay reliability — corrected locally

The former `tools/fit_track.py` read data size from `header_size + 4`, rather
than header offset 4; dropped global message IDs; decoded compressed-header
fields incorrectly; failed to maintain a full timestamp base; and did not
consume developer payloads. Structural errors could silently return a partial
track. Small fixtures reproduced false position records, a dropped compressed
record and reading past the declared data boundary.

The reader now uses the declared boundary, selects global message 20, decodes
compressed timestamps and developer lengths, and raises on malformed/truncated
messages. The observed CC700 container has a two-byte trailer after its last
compressed chunk; it is accepted once the declared decoded length is reached.
CRC validation remains outside this reader. The protocol reference is
[Garmin's FIT specification](https://developer.garmin.com/fit/articles/fit-protocol/fit_protocol.html).

The replay now specifies the device-log timezone explicitly (default
`Europe/Berlin`), exposes held road values and unknown off-route values, and
labels its results as a **vertex-coverage proxy per GPS sample**. It no longer
labels sample counts as blank-map seconds. Missing yaw is not assumed clear.

## What the ride replay establishes now

The acquired ride decodes to **576 distinct GPS timestamps over 598 elapsed
seconds**, with four intervals other than one second. At those sample timestamps,
62 road values and 66 yaw values lack an exact-second log entry. Road values
are held by an explicit model assumption; no missing yaw is invented.

| Model | Absent coverage proxy | Unknown gate proxy | Modeled block switches |
|---|---:|---:|---:|
| v16 | 294/576 samples | 63/576 samples | Not counted |
| v17 with gate bypass | 0/576 samples | 0 from yaw, since bypassed | 3 |

Both rows still depend on held road values and reconstructed section mapping.
The count only tests stored map vertices within a 300 m radius. It does not
execute clipping, projection, polygon filling, label drawing, allocation,
display updates, route replacement or scheduling. A segment can cross the screen
without any vertex inside that radius. The Python point-to-section reconstruction
also differs from an observed +40 payload at shared section endpoints.

The harness compiles the preserved **nearest helper**, not the full loader,
matcher or gate. The separate review probes execute the full loader with address
adapters. Neither is full firmware emulation. The two reported causes remain
well supported by the source/log combination; the old exact duration claims
and “no flicker” claim are not established by this harness.

## Additional mining that changes the next work

**Indexed point access is linear.** Stock `0x4204922c` calls `0x421cfedc`, which
walks from the linked-list head through node +4 once per index. Verified with GNU
Xtensa disassembly, splitting at branch target `0x421cfee8` to avoid padding
misalignment. The patch requests `pt(i)` and `pt(i+1)` on each segment, so the
full scan performs `(point_count - 1)^2` next-link traversals: 312,481 for 560
points, before the extra selected-point read and other work. This is a static
operation count, **not measured latency**. The stock matcher uses an iterator.
Use sequential access for the corrected selector; the Python array callback
cannot reveal this target cost.

**Reroute equivalence remains unresolved.** The existing
[runtime extraction](../research/navigation-runtime-extraction.md) already shows that restart
discards the basemap and loads mode-dependent combinations of original and
connector slots. The new +40-to-map-index assumption must be verified for those
combinations. “No worse than v16” is unsupported: v17 changes both block choice
and whether the map renderer runs in those states. Ordinary route success does
not close this boundary.

**Gate bypass has a bounded direct hook but shared runtime costs.** Its
trampoline replaces the map wrapper and leaves the off-route predicate itself
unchanged. `cc_iter` takes the map mutex and allocates a styled-point buffer;
executing it during phases previously skipped can affect other tasks through
contention, allocation and CPU time. Call-graph separation does not prove zero
indirect effect on recording or replanning.

## Verification and continuation

- v17 ELF and image were rebuilt from the current sibling sources and match the
  saved artifacts byte for byte. Image SHA-256 remains
  `537364660e222139d29c70078850dfceb56f51c26acad728708b2ab121af24d9`.
  `espimg.py` rebuild also matches. DRAM/IRAM segments are unchanged; DROM differs
  by the version byte. Build reproducibility is confirmed, not device acceptance.
- `python3 -m unittest discover -s tools -p test_replay_inputs.py -v`:
  **10/10 pass**, following observed failing fixtures before each correction.
- Preview suite: **5/5 pass**. Historical generator edge suite rerun:
  **10/12 pass**; `GPS recording, 3 m noise` produces 46 turns versus baseline
  15, and `planner export, every 8th point` produces 5. These independent
  generator defects remain. `tools/test_route.mjs` is a generator requiring
  input/output arguments, not a standalone test suite; invoking it bare failed
  for missing arguments and did not validate anything.
- Both nonempty acquired ride tracks still decode to exactly the same positions
  and timestamps as before: 576 and 2,913 records respectively. The parser
  regressions exercise formats and malformed inputs missing from those rides.
- Private source adapters, counterexample probes, original tool snapshots,
  replay output and build verification are in `.local/v17-review-20261114/`.
  No private ride coordinates are included here.

The next firmware change should fix the two selection policies together using
consistent section IDs and sequential traversal, with full-loader regressions
for a stale adjacent section, parallel passes, shared endpoints and crossings.
Then extend that same C seam to ordinary and combined route-file types. Measure
target draw/lock/allocation budgets after the candidate passes these host checks
and a concrete firmware write is approved. The separate generator noise/sparse
cases remain queued; another acceptance ride is premature at this point.
